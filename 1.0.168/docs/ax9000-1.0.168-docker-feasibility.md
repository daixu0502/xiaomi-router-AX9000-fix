# AX9000 1.0.168 增加 Docker 的离线可行性核对

核对日期：2026-10-26。来源为本仓库 `rom/` 中用户提供的两份原厂 ROM。

2026-10-27 进展：已制作 [SSH 部署脚本与原厂页面恢复离线包](../docker/README.md)，补齐独立 API、cgroup 和 procd 托管，固定使用已核对的小米引擎包。已做本地隔离验证，1.0.168 真机容器与浏览器验收仍待完成。下文保留最初离线分析的证据和版本上限边界。

## 结论与验证边界

**1.0.168 可以作为 Docker 移植候选底包，离线检查没有发现必须更换内核的障碍。** 两版实际内核均为 Linux 4.4.60，内嵌的完整内核配置逐字节一致，容器所需的主要配置和模块在稳定版中仍存在。稳定版主要缺少开发版 Docker 的用户空间管理与完整初始化流程。

此结论表示具备移植基础，不表示已经在 1.0.168 真机上成功运行容器。本次只在电脑上分析 ROM，未连接、刷写、重启或修改路由器，也未制作可刷写改包。

## 内核与模块证据

从 UBI kernel 卷内的 FIT 提取 gzip 内核，再从 `IKCFG_ST` 提取配置。两份完整配置的 SHA-256 都是：

`195815e93e5e0d6cfbffe3485d61b8e731c612018b539130695d8a0774a7ebb7`

| 配置 | 两版结果 |
| --- | --- |
| `CONFIG_NAMESPACES`、`UTS_NS`、`IPC_NS`、`USER_NS`、`PID_NS`、`NET_NS` | `y` |
| `CONFIG_CGROUPS`、`MEMCG`、`CGROUP_DEVICE`、`CGROUP_PIDS`、`CGROUP_CPUACCT` | `y` |
| `CONFIG_CPUSETS`、`CGROUP_SCHED`、`CFS_BANDWIDTH` | `y` |
| `CONFIG_OVERLAY_FS`、`EXT4_FS`、`POSIX_MQUEUE` | `y` |
| `CONFIG_BRIDGE`、`BRIDGE_NETFILTER` | `y` |
| `CONFIG_VETH`、`NETFILTER_XT_MATCH_ADDRTYPE`、`IP_NF_TARGET_MASQUERADE` | `m`，对应模块存在 |
| `CONFIG_SECCOMP`、`SECCOMP_FILTER` | 未启用 |

抽查的 `veth.ko`、`xt_addrtype.ko`、`ipt_MASQUERADE.ko` 在两版中逐文件 SHA-256 一致。因此不需要为了补这三个模块而替换稳定版模块。seccomp 缺失是两版共有的限制，不能把此环境视为具备现代 Docker 的全部隔离能力，也不能仅按内核版本安装任意最新版 Docker。

补充核对：1.0.168 的 `CONFIG_EXT4_FS=y`，同时内建 JBD2 和 FS_MBCACHE；USB 存储与 SCSI 磁盘驱动的模块也保留。原厂 `etc/hotplug.d/block/40-mount` 根据 `getdisk fs` 的结果使用 `mount -t 文件系统`，默认自动挂载设置为 `anon_mount=1`，挂载位置为 `/extdisks/设备名`。因此不能说“稳定版不支持 ext4”；Docker 安装脚本复用该支持，并要求先确认实际 ext4 挂载成功。

## Docker 管理组件差异

开发版含有、稳定版缺少的实际文件包括：

- `/etc/config/mi_docker`
- `/etc/init.d/mi_docker`
- `/usr/sbin/mi_docker_disk_manage.sh`
- `/usr/lib/lua/xiaoqiang/module/XQMiDockerUtil.lua`
- `/usr/lib/lua/luci/view/web/setting/docker.htm`
- `/www/xiaoqiang/web/css/docker.css`
- `/www/xiaoqiang/web/img/install-docker.png`

稳定版残留 `/etc/rc.d/S99mi_docker` 链接，但对应服务脚本不存在；不能据此认为 Docker 已安装。

两版 `/etc/init.d/cgroup_init` 不同。开发版额外挂载 cpuset、cpuacct、blkio、devices、pids 等控制器，并设置 Docker 资源组；稳定版没有相同的完整流程。安装时需要补齐 Docker 所需挂载，同时保留稳定版现有资源分组。

两版通用 API 控制器 `usr/lib/lua/luci/controller/api/xqsystem.lua` 内容不同，且 Lua 文件包含小米定制字节码。若要恢复原厂网页体验，需要继续核对页面路由、功能开关、API、存储挂载及热插拔调用，不能整份覆盖旧控制器。

**开发版 ROM 本身也不含 Docker 引擎二进制。** `/etc/init.d/mi_docker` 指定版本 `19.03.15`，安装时从小米 CDN 下载 `docker-19.03.15-ce.tgz`，程序安装到 `/mnt/docker_disk/mi_docker/docker-binaries/`，数据位于 `/mnt/docker_disk/mi_docker/lib/docker/`。因此仅从开发版复制文件，并不能得到完整 Docker 安装。

原厂安装脚本还要求 ext4 磁盘且容量至少 32768 MiB；这是原厂安装器的检查条件，不是 Docker 的普遍硬件最低要求。原厂磁盘管理脚本在“未安装”状态可能删除已有 `mi_docker` 目录，移植时不能原样启用该分支处理旧数据盘。

## 建议实施顺序

1. 先准备稳定版 root/SSH 的独立恢复与备份，不能假设当前开发版 root 在刷入稳定版后自动保留。
2. 保留 1.0.168 的内核、驱动和基础系统，先以持久目录上的可回退安装方式补 Docker 服务；外接 ext4 保存引擎与容器数据。
3. 补齐 cgroup v1 挂载、磁盘就绪等待、模块加载及 procd 托管，适配本项目已有 Docker 自启和代理实现。已有脚本只验证过 1.0.140，不能直接宣称支持 1.0.168。
4. 先验证与现有数据兼容的引擎版本，再验证 `docker info`、本地测试容器、bridge DNS/出网/端口映射、卷持久化及重启恢复。不得直接让未知新版引擎迁移唯一一份旧容器数据。
5. 引擎验证通过后，再决定是否移植原厂网页、另装管理界面或制作 ROM。改包还需另行确认签名、刷写入口和双系统分区恢复，不在本次已验证范围内。

离线分析脚本、解包文件、内核镜像、完整配置和原始 JSON 报告保留于被 Git 忽略的 `.tools/rom-analysis/`，原始 ROM 未修改。SquashFS 提取仅因非 root 无法创建设备节点 `/dev/console` 返回警告；所比较的普通文件均已提取。

参考：[Docker 官方静态二进制安装与运行条件](https://docs.docker.com/engine/install/binaries/)。固件专有结论以本地两份 ROM 的实际内容为依据。

## 补充：刷原版 1.0.168 后通过 SSH 部署，以及版本上限

该路线可行，前提是刷入后已经恢复 root SSH。通过原版固件完成升级，再从可写文件系统安装服务与页面，不需要重新签名原厂升级包。固件重置/OTA 后组件与 SSH 的恢复需另行处理。

部署脚本需要独立补齐 cgroup v1 控制器挂载、外接 ext4 磁盘识别、Docker/配套运行时安装、procd 托管、日志和回退。原仓库自启脚本要求已经存在 `mi_docker` 及 Docker 二进制，不是稳定版的完整安装器。

管理页面有两条实施路径：独立管理页面（如匹配引擎 API 的 Portainer ARM64 版本）；适配原厂后台入口、页面与 API。后者不能靠复制 `docker.htm` 完成，也不应直接覆盖稳定版通用控制器。

2026-10-26 对当前仍为 1.0.140 的实机只读检查结果如下：

| 项目 | 实际值 |
| --- | --- |
| Docker CLI | 19.03.15，API 1.40 |
| dockerd | `dev`，GitCommit `unsupported`，2021-09-13 构建，API 1.40 |
| containerd | 1.3.9 |
| runc | 1.0.0-rc10 |
| iptables | 1.6.2 |
| 存储驱动 | overlay2，后端 extfs |
| cgroup 驱动 | cgroupfs |

所以不能把当前服务器简单记录为“上游未修改的 Docker Engine 19.03.15”。原厂脚本下载包名与 CLI 为 19.03.15，但 dockerd 自报为厂商构建 `dev`。

**最高兼容版本尚未确定。** 当前没有在 1.0.168 上做任何新版 Docker 容器运行验证，也没有找到小米针对该稳定版给出的 Docker 版本支持矩阵。因此不能将 19.03.15、20.10.24、24.x 或其他版本宣称为固件的最高版本。

Docker 官方静态安装说明中的一般内核最低版本，以及 containerd 对 4.x 内核的概括性描述，都不足以保证某个具体发行包在此定制内核上完整工作。反过来，也不能仅因使用 cgroup v1 就认定 Docker 29 不可运行：官方文档说明 29 仍保留 cgroup v1 支持，虽已标为弃用。

实际版本选择必须同时锁定 dockerd、containerd、runc、CLI 和管理页面，使用独立数据目录测试：启动、拉取与解包、容器创建/exec、bridge DNS/出网、端口映射、bind/volume 持久化、资源限制以及服务重启恢复。仅 `docker --version` 或 `dockerd` 成功启动不能证明整套兼容。原数据与现有服务不应承担上限探测。

两版固件共同缺少 seccomp 内核支持，这一隔离限制不会因更换用户空间 Docker 自动补齐。旧引擎只能作为兼容性对照，不据此推荐作为长期最终版本；新版验证通过后再固定发行包和摘要。
